## 3. Quick Wins

*Ship-in-a-sprint items. Ordered severity → leverage → corroboration. Calibration note: this audit found 0 P0/0 P1 in five lenses; per the rubric's sanity-check guidance, well-justified P2 items with small effort, a clear fix, and a concrete cost are admitted to quick-wins (severity ≠ priority).*

**QW1 — Add an ADR for the security hook-guard extension (commit d4f38f7)** · knowledge · `docs/decisions/` · **P1**
The May-12 commit extended the fail-closed credential guard from advisory tools to delegation tools — a trust-boundary change — with no decision record anywhere (only the commit message + `hooks.json`). *Impact:* security-boundary changes without ADRs make intentional-vs-accidental impossible to verify in any future audit; sets a precedent for the next solo-author security change. *Fix:* write one dated ADR (context/decision/status/rationale); adopt "ADR in the same commit" for future security-boundary changes. *Effort:* small (~1h) · *Leverage:* high (security traceability) · cross-links QW6.

**QW2 — Correct the README safety-substrate tool list** · knowledge · `README.md:115` · **P2**
README states the guard covers 3 advisory tools; the matcher actually covers 5 (adds `delegate.start`, `delegate.decide`). *Impact:* the primary reader/security-reviewer entry point *understates* the trust boundary — wrong direction (looks more permissive than reality). *Fix:* one sentence. *Effort:* XS (~15 min) · *Leverage:* high.

**QW3 — Emit a rollback audit event** · operational · `delegation_controller.py` rollback branch (~2209-2255) · **P2**
Promotion `rollback_needed→rolled_back` emits no `append_audit_event`. *Impact:* the forensic surface most likely consulted first (`audit/events.jsonl`) is silent on the highest-risk operation — a rolled-back promotion looks identical to a clean one. This is a clean *additive* forensic gap, **not** a design reversal: `promotion-protocol.md` §Rollback Semantics already records the rollback only in job state and explicitly states "a future rollback audit event may be added when promotion-rejection audit wiring is implemented." *Fix:* still a contract+spec change, not a drive-by call-site add — the `AuditEvent` *record* schema exists but **no `action` enum value covers rollback** (`contracts.md` §Audit Event Actions lists only "currently emitted" + "reserved"): (a) select an action name; (b) add it to `contracts.md` §Audit Event Actions; (c) update `promotion-protocol.md` §Rollback Semantics (state → emitted); (d) emit at the `rolled_back` transition; (e) tests. *Effort:* small · *Leverage:* high. The **unknown-terminal** audit question is deliberately **not** bundled here: emitting an event there would *reverse* a documented design decision (the AuditEvent-vs-OutcomeRecord split) rather than fill an anticipated gap, so it is a decision/provenance question tracked as **Open Question 5**, not a Quick Win.

**QW4 — Add startup Codex-version pre-flight check** · operational · `scripts/codex_runtime_bootstrap.py` `main()` · **P2**
Codex CLI version is enforced only at first delegation call, not at bring-up. *Impact:* `uv sync` + plugin load succeed; a version mismatch surfaces as a mid-session runtime error, not an install-time failure — worse as a distributable plugin. *Fix:* call a version check before `server.run()`, fail fast with a clear message. *Effort:* small (~1-3h) · *Leverage:* high (part of the Codex-CLI cluster — see HL1/ST2).

**QW5 — Document the concurrent-session promotion hazard + add a startup-overlap warning** · operational+knowledge · `README.md:126`, `scripts/publish_session_id.py` · **P2** · *independent_convergence (OP-4 ⋂ KN-5)*
README calls it a "race on the session identity file"; the real worst case is two sessions passing the `HEAD==base_commit` promotion gate and the second `git apply --binary` landing on an already-mutated tree (workspace corruption). *Impact:* operator underestimates severity by ~an order of magnitude; no recovery step documented. *Fix:* expand the Limitations section (what collides, promotion is highest-risk, recovery = stop all/`git status`/single restart) + a cheap mtime-based "session_id written by someone else <60s ago" **startup-overlap warning** on stderr. The warning is a *weak proxy*, **not** race detection: it flags concurrent startup, not the actual promotion TOCTOU — that race is the unlocked precheck→apply window in `delegation_controller.py` (the `HEAD == base_commit` precheck and the `git apply --binary` are separated only by a WAL journal write, with **no cross-process lock**, so two sessions can both pass the gate). The structural fix — a cross-process promotion/session lock around the precheck→apply→verify→rollback critical section — is deliberately **not** bundled here: it is a concurrency change on the trust-boundary mutation path (lock scope, contention behavior, stale-lock recovery, interaction with the WAL journal and the `promotion-protocol.md` state machine), conditional on scale/distribution rather than sprint-ready, so it is tracked as **Watch List WL6**, not a Quick Win — mirroring the QW3 → Open Question 5 split. QW5 buys cheap operator awareness only. *Effort:* small (doc XS + warning ~1-2h) · *Leverage:* medium (awareness only — does not remove the race).

**QW6 — Extract the duplicated trust-boundary tool-name prefix + add a consistency test** · architecture-drift · `scripts/codex_guard.py:24`, `server/consultation_safety.py:76-83` · **P2** · *cross_lens_followup_confirmation (AD-3 ⋂ TD)*
The full MCP prefix string is hardcoded independently in the guard (`codex_guard.py:24` `_TOOL_PREFIX`) and inline in every `_TOOL_POLICY_MAP` key; **no test asserts the two constants are equal directly**. *Impact:* this is **not** an unguarded silent bypass — `test_codex_guard.py` exercises the literal full-prefix tool names through both the clean and secret-block paths, and `test_hooks_coverage.py` binds the hooks matcher to `_TOOL_POLICY_MAP`, so a one-sided prefix rename surfaces as a **hard CI failure**, not silent credential-scan loss. The real debt: this safety invariant is enforced only *indirectly* (an emergent side effect of behavioral tests), never asserted at the source — fragile to a future refactor that changes those tests. *Fix:* shared constant + `assert all(k.startswith(_TOOL_PREFIX) for k in _TOOL_POLICY_MAP)` to make the invariant explicit and refactor-robust. *Effort:* small · *Leverage:* medium.

**QW7 — Fix the `parents[4]` extraction-seam regression in the live test** · architecture-drift+test-debt · `tests/test_control_plane_live.py:21` · **P2** · *cross_lens_followup_confirmation (AD-1 ⋂ TD)*
`parents[4]` resolves to `~` post-extraction (was correct in the monorepo). Masked by the `codex`-absent skip gate in CI; on a dev machine with `codex` present it silently validates `codex.status` against an arbitrary git repo (false green). *Fix:* `parents[4]` → `parents[1]`. *Effort:* XS (one line) · *Leverage:* medium (removes a silent false-green).

**QW8 — Reconcile the stale status synthesis docs** · knowledge · `docs/status/current-state.md`, `reconciliation-register.md` · **P2**
Both carry pre-extraction content dates in their own headers (`current-state.md` "Last updated: 2026-04-29"; `reconciliation-register.md` "Last reconciled: 2026-04-30") — ~15 days before the 2026-05-15 audit and predating the 2026-05-11 extraction, so *every* commit in the standalone history postdates them — yet the README names them the "reader entry point for current project state" and the register is the open-work tracker. *Impact:* orientation friction; the register cannot do its one job. *Fix:* reconcile post-extraction commits; add a new maintenance rule to AGENTS.md's **Workflow Notes** section (no checklist section exists there to extend) — "when a commit changes post-extraction project state, touch the status docs" — mirroring the existing "verify all three locations stay in sync" rule. *Effort:* small (1-2h) · *Leverage:* medium.

**QW9 — Make bounded-poll test failures diagnosable** · test-debt · `tests/test_delegation_controller.py` (~15 sites), `test_resolution_registry_capture_ready.py` / `test_resolution_registry_per_request.py` · **P2**
5s bounded-poll deadlines + a `time.sleep(0.7)` vs 0.5s-timer margin are latent flakes on loaded CI; failures look like real regressions. *Impact:* phantom CI failures erode the single-author project's primary quality signal. *Fix:* widen the thin sleep margin; add `f"...final_job={final_job!r}"` to poll assertions. *Effort:* low · *Leverage:* medium.

## 4. High-Leverage Fixes

*Investing here removes other backlog items. Ordered by downstream count → severity → effort.*

**HL1 — Validate the Codex wire contract in CI (payload shape, not just method names)** · test-debt+dependency · `tests/fixtures/codex-app-server/0.117.0/`, `server/runtime.py` · **P1** · *independent_convergence (TD-2 ⋂ DP-2)*
Vendored schemas are used only to assert client method-name *presence* (`codex_compat.REQUIRED_METHODS ⊆ extracted methods`); no test validates *payload shape*, and the surface splits across **two distinct schema boundaries** that must be tested separately. (1) **Client-request params** — *every* payload `runtime.py` constructs and sends via `JsonRpcClient.request()`: the full `codex_compat.REQUIRED_METHODS` surface — `thread/start` (carries the security-adjacent `approvalPolicy`), `thread/resume`, `thread/fork`, `thread/read`, `turn/start` (carries `sandboxPolicy` / `approvalPolicy` / `effort`), `turn/interrupt` — **plus** the two builders *outside* `REQUIRED_METHODS` — `account/read` and `initialize` (the startup handshake: `runtime.py` sends a structured `clientInfo` payload via `request("initialize", …)`; `test_codex_compat.py::test_vendored_schema_contains_initialize` already proves the *method* is vendored, so the residual gap is purely payload-shape, identical to the rest) — each validated against its client-request param schema. (Scoping to `turn/start` + `account/read` alone — *or* to `REQUIRED_METHODS` + `account/read` without `initialize` — leaves the `thread/*`, `turn/interrupt`, and startup-`clientInfo` builders — including `thread/start`'s `approvalPolicy` — unvalidated.) (2) **Server-request responses** — the approval / file-change / user-input results the controller builds in `_server_request_handler` and sends via `JsonRpcClient.respond()` as JSON-RPC *responses* (`{id, result}`, no `method` — these do **not** travel as a client request method, so there is no `command-respond` surface to validate) — validated against the vendored `*ApprovalResponse` / `ToolRequestUserInputResponse` schemas. A field rename (`approval_policy`→`approvalPolicy`) passes all 1172 tests; the only catch is `test_codex_compat_live.py`, skipped in CI. *Unblocks:* the entire Codex-CLI cluster — DP-1 pin upgrades (ST2), DP-2 CI gap, OP-3 contract drift, and the security-adjacent approval/sandbox payload risk. *Fix:* add `jsonschema` dev dep; **two** contract-test families — one building client-request params through the `runtime.py` request paths, one building server-request responses through the `_server_request_handler` / `respond()` path — each `jsonschema.validate()`d against the matching already-vendored schema. *Effort:* medium · *Leverage:* high (unblocks dependency + operational + closes a security-adjacent gap).

**HL2 — Make the test suite fast (inject the approval window; fast/slow split)** · test-debt · `tests/test_delegation_controller.py`, `pyproject.toml` · **P1**
~245s of the 250s suite is ~6 timeout-path tests parking on the real 900s-default approval window (never injected; `_build_controller` has no override). No `fast`/`slow` markers, no `addopts`, no `pytest-xdist`. *Unblocks:* every other test-coverage recommendation (HL1, HL5) can be added without worsening an already-discouraging 4-min loop; reduces "push and wait for CI" behavior. *Fix:* injectable `approval_window_seconds` (0.5s in timeout tests); `slow` marker + `addopts="-m 'not slow'"` as the **local default only**. A global `addopts` applies to *every* invocation including CI's `uv run pytest tests -q`, so the CI workflow must **explicitly override it to run the full suite** (e.g., `-m ''` / `--override-ini` / an explicit marker) — otherwise the ~6 timeout-path tests (the highest-risk coverage this very item is about) are silently dropped from CI. Consider `-n auto` in CI. *Effort:* medium · *Leverage:* high (prerequisite to safely growing coverage).

**HL3 — Extract `_server_request_handler` from `_execute_live_turn`** · code-health · `server/delegation_controller.py:971-1364` (handler) within `_execute_live_turn` (946-1428) · **P2** · *cross_lens_followup_confirmation (CH-1 ⋂ AD-5)*
A ~394-LOC nested closure (`_server_request_handler`, lines 971-1364, ~37 branches, 3 nonlocal write-back side-channels) inside the ~483-LOC `_execute_live_turn` enclosing method is the sole router for all approval-request kinds. architecture-drift confirmed the *module* is correctly partitioned (no split needed) — the debt is purely this method. *Unblocks:* individual approval-kind handlers become unit-testable in isolation (a test-debt enabler); collapses 2-3 indentation levels. *Fix:* extract to a named `_ServerRequestRouter`/method with explicit params/returns — pure in-module refactor. *Effort:* medium · *Leverage:* medium (test isolation of the approval path).

**HL4 — Two store-hygiene work items: replay caching, and retention/cleanup wiring** · operational · `server/lineage_store.py`, `server/turn_store.py` · **P2**
Both stores reconstruct state by replaying the full JSONL on every read (`LineageStore._replay()` per lineage resolve; `TurnStore._replay()` per `get`/`get_all`/`get_all_checked`) — O(n) per call, growing with dialogue length. Separately, session dirs can orphan on abnormal exit. These are **two independent work items** with different shapes; size and schedule them separately:
- **HL4a — In-memory replay cache.** Memoize the replay result and invalidate on write — but the two stores have **different writer topologies** and must *not* be treated symmetrically (the "single-writer per session, applies to both" assumption is false for `LineageStore`, and contradicts HL4b/OQ4's own "lineage again at the delegation path"). `TurnStore` is constructed **once per session** (`codex_runtime_bootstrap.py` `_build_dialogue_factory` only — `DelegationController` gets no `TurnStore`), so per-instance invalidate-on-append is safe and the cache is a pure in-module change. `LineageStore` is constructed **twice per session** — `_build_dialogue_factory` *and* `_build_delegation_factory` — and both instances persist to the **same** per-session JSONL (`contracts.md` §Crash Recovery Contract: lineage store "shared across capability classes"; the bootstrap factory docstring confirms "Both factories write to the same underlying lineage JSONL file"). A cache invalidated only by its *own* instance's `append()` therefore returns **stale handles** after the other controller writes — a routing/recovery **correctness** bug, not a perf nicety. The `LineageStore` variant requires one of: file mtime/size-based invalidation, a single shared per-session `LineageStore` instance, or scoping the cache to `TurnStore` only (defer lineage caching until cross-instance invalidation exists). *Unblocks:* the dialogue/delegation scaling surface (each dispatch resolves lineage). *Effort:* small (`TurnStore`) → small–medium (`LineageStore`, adds cross-instance invalidation) · *Leverage:* medium-high.
- **HL4b — Retention/session cleanup with an explicit owner and call site.** Current reality (verified 2026-05-16): `LineageStore.cleanup()` *exists* but has **no production call site** (only `tests/test_lineage_store.py`); `TurnStore` has **no `cleanup()` method at all**. Both stores are constructed in `scripts/codex_runtime_bootstrap.py` (lineage+turn at the dialogue path, lineage again at the delegation path) with no teardown wired. Work: add `TurnStore.cleanup()`; add a single owning teardown call site covering normal *and* abnormal exit in the bootstrap/runtime lifecycle; decide the abnormal-exit retention policy (cleanup vs. retain-for-inspection, consistent with `recovery-and-journal.md` §Retention Defaults). *Effort:* medium · *Leverage:* medium. Evidence in Open Question 4 (now resolved).

**HL5 — Add a real-subprocess test layer for `JsonRpcClient`** · test-debt · `server/jsonrpc_client.py` · **P2**
`request()` / `next_notification()` and the malformed-line silent-drop (`except json.JSONDecodeError: continue`) are untested in the non-live suite; a dropped notification the controller awaits → hang/timeout, unexercised. *Unblocks:* safe evolution of the transport layer (all higher tests use fakes). *Fix:* `tests/test_jsonrpc_client.py` driving a trivial echo subprocess (not the Codex binary; <1s, CI-safe) for round-trip / notification-buffer / malformed-drop / ID-mismatch. *Effort:* medium · *Leverage:* medium.

## 7. Tradeoff Map

*Resource-allocation tensions with concrete anchors — for capacity planning, not design debate.*

**TR1 — Refactor ↔ Ship** (anchor: `delegation_controller.py:971`)
HL3 (extract the ~394-LOC closure) competes directly with feature work for the **only** contributor's time. The closure isn't touched every PR, so the compounding cost is real but slow — but it also gates ST1 (knowledge transfer is far cheaper after extraction). Spending on HL3 buys down ST1; deferring both compounds approval-routing change-friction *and* handoff risk together.

**TR2 — Test Coverage ↔ Deploy Speed** (anchor: `.github/workflows/ci.yml`, `pyproject.toml`)
The audit *recommends adding* contract coverage (HL1) and a transport test layer (HL5) onto a suite that is already a discouraging 4 minutes (HL2). Adding coverage first makes the loop worse; HL2 (fast/slow split, window injection, xdist) is the **prerequisite** that makes HL1/HL5 free to land. Sequence HL2 → HL1 → HL5. Doing HL1 before HL2 is the trap.
