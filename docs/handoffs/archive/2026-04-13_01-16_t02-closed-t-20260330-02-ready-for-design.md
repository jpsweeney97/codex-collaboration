## Decisions

### Decision 1: Keep `recover_startup()` using `get_all()` instead of `get_all_checked()`

**Choice:** Keep the current asymmetry where `_next_turn_sequence()` uses diagnostics-aware `get_all_checked()` but `recover_startup()` uses plain `get_all()`.

**Driver:** User's review analysis: "`_next_turn_sequence()` needs diagnostics because it has an empty-store fast path that can otherwise incorrectly assume 'no turns have ever completed.' `recover_startup()` already does a remote `thread/read` before deciding eligibility, so diagnostics do not close the same correctness gap."

**Alternatives considered:**
- **Switch `recover_startup()` to `get_all_checked()`** — would make both sites symmetric. Rejected because diagnostics are file-global (session-wide JSONL), so unrelated corruption from another collaboration would influence reattach policy. User: "Using file-global diagnostics in startup recovery would also be a much blunter signal, because unrelated corruption elsewhere in the session file could start influencing reattach policy."

**Trade-offs accepted:** Recovery path doesn't detect JSONL corruption — only checks prefix-completeness of whatever metadata it can read. A handle with corrupt JSONL but valid metadata would pass recovery. Acceptable because the next `reply()` call invokes `_next_turn_sequence()` which does have diagnostics-awareness.

**Confidence:** High (E2) — rationale grounded in both the trust model difference and the blast-radius analysis of file-global diagnostics.

**Reversibility:** Medium — adding diagnostics to recovery later requires changing `get_all()` to `get_all_checked()` and handling the new diagnostic signal. The two pinning tests would need to be updated to match the new policy.

**Change trigger:** If a scenario arises where corrupt JSONL causes recovery to reattach a handle that should be quarantined, and the `_next_turn_sequence()` catch on the next `reply()` is too late (data already written or side effects fired).

### Decision 2: Keep extra-local warning only in `_next_turn_sequence()`, not in `recover_startup()`

**Choice:** Leave the stderr warning for extra-local keys in the reply path only. Recovery path silently accepts extra-local keys.

**Driver:** User's review analysis: "The warning in `_next_turn_sequence()` is useful because it fires exactly when stale metadata is about to matter for dispatch and then be overwritten. Emitting the same warning during startup would add observability, but it would also duplicate noise across restarts without changing recovery correctness."

**Alternatives considered:**
- **Add warning to `recover_startup()` too** — would make observability symmetric. Rejected because restarts produce the warning every time, creating noise without a corresponding correctness benefit. User: "That looks like a follow-up observability choice, not a review blocker."

**Trade-offs accepted:** Recovery path silently accepts what the reply path warns about. Acceptable because the warning is observability, not enforcement — both paths tolerate extra-local keys.

**Confidence:** High (E1) — single-source rationale (user's analysis) but the argument is self-contained.

**Reversibility:** High — adding the warning later is a one-line change.

**Change trigger:** If operational experience shows that extra-local keys during recovery indicate a problem that needs attention.

### Enforcement site asymmetry (the design decision pinned by tests)

| Site | Method used | Diagnostics? | Trust signal | Why |
|------|------------|--------------|-------------|-----|
| Reply path (`_next_turn_sequence`) | `get_all_checked()` | Yes | Local metadata only | Empty-store fast path needs to distinguish "no turns" from "corrupt store" |
| Recovery path (`recover_startup`) | `get_all()` | No | Remote `thread/read` | Remote completed-turn count provides the trust signal; file-global diagnostics are too blunt for reattach decisions |

This asymmetry is now documented in three places: (1) the commit message for `3bdc3859`, (2) the test docstrings, and (3) the open questions resolution in this handoff.

**Why file-global diagnostics are problematic for recovery:** `ReplayDiagnostics` at `replay.py:44-53` collects issues from the entire session-wide JSONL file, not from a single collaboration. A corrupt line from an unrelated collaboration would appear in the diagnostics. Using this in `recover_startup()` means unrelated corruption could prevent reattaching a perfectly valid handle. The `_next_turn_sequence()` path accepts this risk because its empty-store fast path is a higher-stakes decision (proceeding as turn 1 when turns have actually completed).

### T-02 dependency graph (complete picture)

```
replay_jsonl() [shared foundation]
    -> collects ReplayDiagnostics (file-global)
    -> filters by collaboration_id for metadata

get_all_checked() [reply path]
    -> calls replay_jsonl()
    -> returns (dict[int, int], ReplayDiagnostics)

get_all() [recovery path]
    -> calls replay_jsonl()
    -> returns dict[int, int] only (diagnostics discarded)

_local_metadata_complete_for_completed_turns() [shared invariant]
    -> pure function: (local_turns, completed_count) -> bool
    -> completed_count == 0: returns `not local_turns`
    -> completed_count > 0: returns `{1..N}.issubset(keys)`

_next_turn_sequence() [USES get_all_checked + shared invariant]
    -> Phase 1: empty store + no diagnostics → fast path return 1
    -> Phase 2: all other states → read_thread() for remote truth
    -> Phase 3: prefix-completeness gate via shared invariant

recover_startup() [USES get_all + shared invariant]
    -> reads remote via thread/read
    -> calls shared invariant unconditionally
    -> quarantines handle on prefix-completeness failure
```

### Test patterns used in the pinning tests

**Store path construction:** `tmp_path / "plugin-data" / "turns" / "sess-1" / "turn_metadata.jsonl"` — the `plugin-data` prefix comes from `_build_dialogue_stack()` at `test_dialogue.py:33`.

**JSONL corruption injection:** Append invalid JSON directly to the store path file via `store_path.open("a")`. This simulates mid-session corruption without requiring mock infrastructure.

**`read_thread_response` override:** Set `session.read_thread_response = {"thread": {"id": "...", "turns": [...]}}` to control what `read_thread()` returns. Each turn entry needs `{"id": "turn-N", "status": "completed"}`.

## Learnings

### Pinning tests document design decisions more durably than comments

**Mechanism:** When two enforcement sites intentionally diverge, the divergence is a design decision. A comment explains it; a pinning test enforces it. The test's docstring serves as the design rationale, and the test itself prevents accidental "fixes" that eliminate the intentional asymmetry.

**Evidence:** The two recovery-diagnostics tests added this session. Their docstrings explain *why* `recover_startup()` ignores diagnostics (trust model difference). If someone later adds diagnostics to recovery, these tests fail — forcing them to read the rationale and make a conscious choice.

**Implication:** For future intentional asymmetries between enforcement sites, add pinning tests that assert the current behavior and document the rationale in docstrings. The test suite becomes the authoritative record of design decisions, not just behavioral verification.

### Ticket closure should map back to acceptance criteria, not just list changes

**Mechanism:** A resolution section that only describes what changed is a changelog entry. A resolution that maps changes back to the original acceptance criteria proves completeness — each criterion is addressed, and any gaps are visible.

**Evidence:** The T-20260410-02 resolution references "all 5 acceptance criteria met" and lists the specific deliverables that satisfy each one. Future readers can verify closure without re-reading the PR.

**Implication:** When closing tickets, map the resolution to the acceptance criteria explicitly. This is especially important for tickets with multiple independent criteria, where it's easy to close after shipping most but not all deliverables.
