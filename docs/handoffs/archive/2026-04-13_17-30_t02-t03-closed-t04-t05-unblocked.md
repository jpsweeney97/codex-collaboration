## Decisions

### Decision 1: Accept that MCP server ships dialogue tools in T-02 consult-only scope

**Choice:** Do not strip `codex.dialogue.*` tools from `TOOL_DEFINITIONS` in `mcp_server.py`. The "consult only" scope is enforced at the skill layer via `allowed-tools`, not at the MCP tool surface.

**Driver:** User's analysis: "The ticket itself already acknowledges that the package exposes `codex.status`, `codex.consult`, and the R2 dialogue tools today." The ticket's `Explicitly out of scope` section lists "Dialogue orchestration," not "dialogue tools."

**Alternatives considered:**
- **Strip dialogue tools from TOOL_DEFINITIONS** — would make the MCP surface match the ticket summary. Rejected because it would require re-adding them in a later ticket (pure churn) and because deferred dialogue initialization already isolates dialogue from the consult path.

**Trade-offs accepted:** The installed plugin exposes tools that aren't surfaced through skills. A consumer calling MCP tools directly could invoke dialogue tools without the skill-layer boundary. Acceptable because MCP tools are machine-facing, not user-facing.

**Confidence:** High (E2) — both the ticket text and the `test_status_works_without_dialogue`/`test_consult_works_without_dialogue` tests at `test_mcp_server.py:459-500` confirm functional independence.

**Reversibility:** High — adding or removing tools from `TOOL_DEFINITIONS` is a localized change.

**Change trigger:** If the dialogue tools on the MCP surface cause problems for consumers who shouldn't have access to them (e.g., permission prompt noise).

### Decision 2: Verify and close T-03 rather than write a design doc

**Choice:** Treat T-03 as a verification pass, not a design/implementation task. All 8 acceptance criteria already have implementations.

**Driver:** User's correction of the initial matrix: "The matrix's main mistake is not overclaiming implementation; it is underclaiming what is already done." Specific evidence for all 8 ACs.

**Alternatives considered:**
- **Write a design doc focused on analytics emission** — the initial recommendation before the user corrected the matrix. Rejected because analytics emission already exists (`OutcomeRecord`, `journal.append_outcome()`) and designing a "new" system would reopen an existing subsystem.
- **Write a formal verification plan** — heavyweight for a pass that can be executed directly. Rejected by user: "the next artifact should probably be a verification-and-doc-alignment pass, not a design doc."

**Trade-offs accepted:** No new design documentation produced for T-03. The ticket closure resolution section serves as the verification record. If future maintainers need deeper design context, they'll need to read the spec docs directly.

**Confidence:** High (E2) — verified each AC against implementation evidence with file:line citations and ran the full 566-test suite.

**Reversibility:** High — reopening a closed ticket is trivial if verification evidence is later found insufficient.

**Change trigger:** If a subsystem is found to be incorrectly implemented (not just present) during T-04 or T-05 work.

### Skill-layer vs MCP-layer boundary

The plugin has two API surfaces:

| Layer | Audience | Tools exposed | Boundary mechanism |
|-------|----------|---------------|-------------------|
| MCP tools (`TOOL_DEFINITIONS` in `mcp_server.py:15-83`) | Machine consumers | All 5: `codex.status`, `codex.consult`, `codex.dialogue.start/reply/read` | Server code |

Agent-internal skills (e.g., `dialogue-codex`) are not user-invocable and may reference dialogue tools — they are subagent behavioral contracts.

### Safety substrate wiring chain

The credential scanning chain for advisory tool calls:

```
hooks.json (PreToolUse matcher for codex.consult, dialogue.start, dialogue.reply)
  -> codex_guard.py (fail-closed: exit 2 on parse/input/internal error)
    -> consultation_safety.py (per-tool ToolScanPolicy: CONSULT_POLICY, DIALOGUE_START_POLICY, DIALOGUE_REPLY_POLICY)

        -> secret_taxonomy.py (pattern definitions, placeholder bypass)
```

`codex.status` and `codex.dialogue.read` are excluded from the hook matcher — status has no user content, read is a query.

## Learnings

### Glob-based subsystem detection fails when naming diverges from predecessors

**Mechanism:** Searching for `*analytic*` found zero files in codex-collaboration, leading to a false "missing/greenfield" classification. The implementation uses `OutcomeRecord` and `journal.append_outcome()` — vocabulary that diverged intentionally during the greenfield rewrite.

**Evidence:** User corrected the matrix with specific file:line citations: `models.py:160`, `journal.py:183`, `control_plane.py:228`, `dialogue.py:256`, `test_outcome_shape_consistency.py:28`.

**Implication:** When auditing subsystem presence in a greenfield rewrite, search by semantic function (e.g., "what emits outcome records?") not by predecessor naming. The `decisions.md` greenfield rules explicitly replace naming conventions.

### Tickets written as a batch may be pre-satisfied by incremental implementation

**Mechanism:** When a ticket batch is authored at a planning milestone, implementation may land incrementally before individual tickets formally open. The closing work becomes verification against acceptance criteria rather than implementation.

**Evidence:** Three tickets in sequence (T-20260410-02, T-20260330-02, T-20260330-03) all had implementations predating their closure sessions. T-02 had all 5 named artifacts. T-03 had all 6 subsystems implemented.

**Implication:** For remaining supersession tickets (T-04 through T-07), start with a gap matrix before assuming greenfield work. Read existing code first.

### User-invocable vs agent-internal is a load-bearing distinction for boundary tests

**Mechanism:** The `dialogue-codex` skill exists in the skills directory but is not user-invocable — it's a subagent behavioral contract. A boundary test that asserts "no dialogue skill exists" fails; a test that asserts "no user-invocable dialogue skill exists" correctly passes.

**Evidence:** Initial `test_no_dialogue_skill_exists` failed on `{'dialogue-codex'}`. Fixed by checking `user-invocable` in YAML frontmatter.

**Implication:** When writing boundary assertions against the skill directory, always filter by `user-invocable: true` to distinguish user-facing skills from agent-internal contracts.
