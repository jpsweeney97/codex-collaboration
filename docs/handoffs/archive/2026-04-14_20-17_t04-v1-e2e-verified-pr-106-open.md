## Codebase Knowledge

### Transcript JSONL structure

Transcript entries use a wrapper structure, not bare Claude API messages:

```
{
  "parentUuid": "...",
  "isSidechain": true,
  "agentId": "ac2de38acdc72d2e3",
  "message": {
    "model": "claude-opus-4-6",
    "id": "msg_...",
    "type": "message",
    "role": "assistant",
    "content": [...]
  },
  "requestId": "req_...",
  "type": "assistant",
  "uuid": "...",
  "timestamp": "2026-04-14T18:46:17.453Z",
  ...
}
```

The `role` field is nested inside `message`, not at the top level. The `type` field at the top level differs from `message.type`. Tool calls are `content` blocks with `type: "tool_use"` inside `message.content`. Tool results are `content` blocks with `type: "tool_result"` in user-role entries.

## Learnings

### Terminal agent message is not in the transcript JSONL

**Mechanism.** Claude Code agents terminate when they produce a message with no tool calls. SubagentStop fires at termination and copies the transcript. But the final message has not been persisted to the transcript file at that point. The final message IS returned to the parent through the Agent tool's return value.

**Evidence.** Transcript JSONL has 66 entries, with the last assistant message at line 64 (turn 5, `terminal: false`). The orchestrator's return output contains turn 6 (`terminal: true`) with epilogue and `<PRODUCTION_SYNTHESIS>`. Checked lines 65-66 — they contain a tool call (codex_dialogue_reply) and its result, not the terminal message.

**Implication.** Any future tooling that operates on transcript JSONLs (automated rubric checkers, transcript analyzers, audit scripts) must know the terminal state is in the return path, not the JSONL. The JSONL captures the dialogue process; the return captures the conclusion.

**Watch for.** This also applies to shakedown runs — `shakedown-dialogue`'s terminal state block would be absent from its transcript JSONL too. Any rubric automation must use a different source for terminal checks.

### Stale cleanup script requires CLAUDE_PLUGIN_DATA when run from parent context

**Mechanism.** `clean_stale_shakedown.py` reads `CLAUDE_PLUGIN_DATA` to find the shakedown data directory. When run from a hook, the environment variable is set by Claude Code. When run manually from the parent session (as in this E2E test), it's not set and the script fails.

**Evidence.** First invocation failed: `clean_stale_shakedown failed: CLAUDE_PLUGIN_DATA not set. Got: ''`. Fixed by prepending the env var: `CLAUDE_PLUGIN_DATA=/Users/jp/.claude/plugins/data/codex-collaboration-inline python3 ...`.

**Implication.** The `/dialogue` skill's step 4 (stale cleanup) works correctly when invoked as a skill (Claude Code sets the env), but manual testing requires explicit env setup. The report documents this for future manual verification.

**Watch for.** Other scripts that depend on `CLAUDE_PLUGIN_DATA` will have the same issue when tested outside the hook/skill context.

### Query intent field is `type`, not `intent`

**Mechanism.** The per-turn contract's scouting queries use `type` as the field name for query intent (values: `definition`, `falsification`). The rubric inspection script initially checked for `intent`, finding no matches.

**Evidence.** Turn 2 queries: `{"type": "definition", "tool": "Read", ...}`, `{"type": "falsification", "tool": "Grep", ...}`.

**Implication.** Any future automated rubric tooling must use `type` for query intent discrimination. The field name is established in the emission contract at `dialogue-codex/SKILL.md`.

**Watch for.** Field naming inconsistency — `type` is overloaded (message type, content block type, query type). Context disambiguates but automated parsers need explicit field paths.

## Gotchas

### Transcript JSONL message structure has a wrapper

**Symptom:** Parsing transcript entries for `role` or `content` at the top level returns nothing — these fields are nested inside `message`.

**Root cause:** Claude Code transcript entries use a wrapper structure with fields like `parentUuid`, `isSidechain`, `agentId`, `type`, and `message`. The actual API message (with `role`, `content`) is inside `message`.

**Prevention:** Always access via `entry["message"]["role"]` and `entry["message"]["content"]`, not `entry["role"]`.

### `clean_stale_shakedown.py` needs CLAUDE_PLUGIN_DATA when run manually

**Symptom:** Script fails with `clean_stale_shakedown failed: CLAUDE_PLUGIN_DATA not set. Got: ''` when invoked from a manual test.

**Root cause:** The script reads `CLAUDE_PLUGIN_DATA` for the data directory path. When run from a hook or skill, Claude Code sets this env var. When run manually, it's unset.

**Prevention:** Set the env var explicitly: `CLAUDE_PLUGIN_DATA=/Users/jp/.claude/plugins/data/codex-collaboration-inline python3 scripts/clean_stale_shakedown.py`.

### Query intent field is `type`, not `intent`

**Symptom:** Rubric check for scouting queries finds zero matches when filtering on `query.intent`.

**Root cause:** The emission contract uses `type` as the field name for query intent. The name `intent` was assumed from the rubric description.

**Prevention:** Use `query["type"]` for intent discrimination (values: `definition`, `falsification`).
