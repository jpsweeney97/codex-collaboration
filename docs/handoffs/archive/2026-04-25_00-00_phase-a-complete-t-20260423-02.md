## Decisions

### Modularize the 6155-line plan via mechanical hand-split

**Decision:** Convert monolithic plan to manifest + 8 phase files using sed + printf, NOT `/superspec:spec-writer`.

**Driver:** User stated: "Prefer mechanical hand-split unless `/superspec:spec-writer` can be constrained to no semantic edits. If `/superspec:spec-writer` does ensure no semantic edits, then use that because it has a corresponding review team skill that would be useful."

**Rejected:** `/superspec:spec-writer` — risk of semantic drift across the split. The review-team skill benefit didn't outweigh that risk for plan content where byte-exactness matters.

**Implication:** Each phase file is independently dispatchable. Subagents read only their phase, not the full plan. Coordinator (me) carries cross-phase context.

**Trade-offs:** Manual maintenance burden if cross-cutting plan edits are needed (e.g., the import-path fix required sed across 8 files). Accepted because cross-cutting edits are rare.

**Confidence:** High (E2) — verified via byte-exact comparison post-split that task numbers, test bodies, invariants preserved.

**Reversibility:** High — the manifest can re-merge phase files trivially if needed.

**Change trigger:** If subagents start carrying cross-phase context implicitly (e.g., adapting Task N+1 based on Task N's completion), modularization isn't enforcing the boundary. Re-evaluate.

### Subagent-Driven Development with sequential per-task dispatch

**Decision:** Execute Phase A using `superpowers:subagent-driven-development` skill — fresh subagent per task, spec compliance review, code quality review, coordinator review between tasks.

**Driver:** User: "Execution: Subagent-Driven, sequential per task, with phase checkpoints and extra coordinator scrutiny around Tasks 15-19" (Tasks 15-19 land R13/R14 invariants).

**Rejected:** Inline batch execution (executing-plans skill) — would have me execute all tasks in current context, accumulating state across tasks. Subagents enforce TDD discipline naturally and isolate each task's context.

**Implication:** ~3× subagent invocations per task (implementer + spec reviewer + quality reviewer). Higher cost but tighter quality gates. Each task gets independent verification.

**Trade-offs:** Slower wall-clock per task (~5-10 minutes per task end-to-end). Accepted for quality.

**Confidence:** High (E3) — pattern explicitly recommended by writing-plans skill output handoff and validated by 5 Phase A tasks landing cleanly.

**Reversibility:** Medium — could switch to executing-plans for later phases, but that would lose the per-task review checkpoints.

**Change trigger:** If subagent dispatch starts producing significantly different work than expected (e.g., implementer makes architectural decisions plan didn't anticipate), reconsider model tier or break tasks smaller.

### Patterns Identified

- **Module-private convention:** Underscore-prefixed names (`_sanitize_error_string`, `_WorkerTerminalBranchSignal`, `_TERMINAL_STATUS_MAP`) are not exported. No `__all__` block in this file.
- **Exception design discipline:** Public errors inherit `RuntimeError` (e.g., `DelegationStartError`); internal assertion signals inherit `Exception` directly (e.g., `UnknownKindInEscalationProjection`, `_WorkerTerminalBranchSignal`). This pattern matches `replay.py`'s `SchemaViolation` and `UnknownOperation`.
- **Class-level annotations on `DelegationStartError`** (`reason: str`, `cause: Exception | None`) before `__init__` are documentation-only at runtime; instance attributes are set inside `__init__`. **This pattern is style-divergent from `replay.py`'s exception classes** (which don't use class-level annotations) — minor finding, deferred per policy.
- **Logger usage:** `logger = logging.getLogger(__name__)` at module level. Used in `_sanitize_error_string` warning. Caught `_WorkerTerminalBranchSignal` should log `signal.reason` (not `str(signal)`, which is empty due to dataclass `args=()`).

### Conventions Observed

## Learnings

### Plan defects classify into 3 patterns, all best fixed at plan layer

**Mechanism:** Plan defects in Phase A fell into three classes:
1. **Literal-text errors** — fabricated paths (test_recovery.py), wrong import prefixes (codex_collaboration.server.*), non-existent test directories (tests/unit/).
2. **Test-logic defects** — vacuous assertions (test_sanitize_caps_total_at_256_chars).
3. **Documentation ambiguity** — docstring underspecification (200 chars truncation order).

**Evidence:** All three classes manifested in Phase A. All three were resolved with single plan-layer commits (`68755ad0`, `58218e09`, `ca64ab34`).

**Implication:** Future plan reviews should explicitly probe for these three classes BEFORE execution. R15/R16/R17 caught some pre-execution; the import-path defect surfaced post-Task-1 only because the implementer silently adapted.

**Watch for:** A plan that passes "literal-text" review can still hide test-logic vacuity (a test that always passes). Manual review of cap/boundary tests should compute the arithmetic.

### Deviation-disclosure protocol catches transparency gaps

**Mechanism:** Task 1's implementer silently adapted the import path from `codex_collaboration.server.*` (plan sample) to `server.*` (project convention). The adaptation was correct, but the lack of disclosure delayed identification of the underlying plan defect by one task cycle.

**Evidence:** Code quality reviewer for Task 1 caught the discrepancy by inspecting the actual test file imports vs. the plan sample. After this, all subsequent implementer prompts included an explicit deviation-disclosure protocol. Tasks 2-5 implementers properly disclosed every deviation (line drift in Task 2, dataclass-import addition in Task 5).

**Implication:** Implementer prompts MUST require explicit deviation disclosure. The protocol prevents "silent correctness" from masking plan defects.

**Watch for:** Subagents may hesitate to disclose adaptations they consider obvious. Prompt language should make disclosure unconditional ("EVEN IF your adaptation is correct").

### Pyright cache vs. runtime: tests are ground truth

**Mechanism:** Pyright's static analysis runs on a cached representation of files. After file edits, Pyright may show stale "unknown import symbol" errors that the runtime resolves correctly.

**Evidence:** Across Tasks 1-5, Pyright repeatedly emitted "X is unknown import symbol" diagnostics for newly-added symbols, but `pytest -v` showed all tests passing. Independent runtime checks (`python -c "from X import Y; print(Y)"`) confirmed runtime resolution worked.

**Implication:** Pyright diagnostics need triage by category: cache-staleness (ignorable), expected per-plan (e.g., the line :965 type error is documented in commit message), real (rare).

**Watch for:** If Pyright emits a NEW kind of diagnostic that isn't a cache artifact and isn't documented in the plan, it's a real finding.

### Dual-oracle test pattern is unusually rigorous

**Mechanism:** Task 5's `test_does_not_propagate_through_runtime_error_except` proves that `_WorkerTerminalBranchSignal` cannot be caught by `except RuntimeError`. The test uses two independent oracles:
1. **Static (Pyright):** The except RuntimeError block is type-statically unreachable; Pyright emits "unreachable code" diagnostic.
2. **Runtime (pytest):** If somehow the block executed, `pytest.fail()` would fire.

**Evidence:** Pyright emitted exactly the unreachable diagnostic at line 37. If a future refactor accidentally inherits from RuntimeError, BOTH oracles would alarm: Pyright loses the unreachable diagnostic AND the runtime would actually execute pytest.fail.

**Implication:** This pattern is generalizable to any "X must NOT be Y" property. The dual-oracle approach catches regressions that a single oracle would miss.

**Watch for:** Pyright "unreachable" diagnostics on test code may be flags of dual-oracle design rather than bugs. Inspect intent before reporting.

### `frozen=True` dataclass + Exception inheritance is legal Python and correct sentinel design

**Mechanism:** Python allows `@dataclass(frozen=True) class X(Exception):` — the dataclass decorator generates `__init__`, `__eq__`, `__hash__`, `__repr__`, while Exception inheritance allows `raise` and `except`. `frozen=True` makes instances hashable (necessary for Python sentinel semantics).

**Evidence:** `_WorkerTerminalBranchSignal(Exception)` with `@dataclass(frozen=True)` and single `reason: str` field works correctly across all 5 Task 5 tests.

**Implication:** When a sentinel needs structured payload (vs. a singleton), `@dataclass(frozen=True)` Exception subclass is the right pattern. `args` will be empty (`str(instance) == ""`) so log/error code must access fields directly (`signal.reason`), not via `str(signal)`.

**Watch for:** Logging/error code that uses `str(exc)` on a caught `_WorkerTerminalBranchSignal` will get an empty string. **Task 15 catch-site implementer should log `signal.reason` explicitly** (carry-forward item).
